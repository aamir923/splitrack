# SQL / Database Principles (gave)

## 1. PostgreSQL
Relational DB with strong transactions (ACID), constraints, and rich types (UUID, TIMESTAMPTZ, JSONB). Right fit for money data where consistency matters.

## 2. UUID primary keys
- Not guessable or enumerable (`/users/1`, `/users/2`...).
- Can be generated by the app without a DB round trip.
- Safe to merge across services/systems.
- Trade-off: larger than integers; random UUIDs can fragment indexes (UUIDv7 is time-ordered and helps).

## 3. Schema migrations with Flyway
Schema changes live in versioned SQL files (`V1__create_users.sql`, `V2__...`). Flyway applies them in order and records them in a history table.
- Never edit a migration that has already been applied. Add a new one.
- The schema is then reproducible on every environment.

## 4. Constraints enforce rules in the database
- `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK`.
- `UNIQUE (provider, provider_subject)` guarantees one Google account maps to one identity row.
- App code can have bugs; constraints are the last line of defense.

## 5. One-to-many relationship
One `users` row to many `user_identities` rows. The child holds the foreign key (`user_id`).

## 6. Normalization
Keep each fact in one place. Identity data is separate from profile data, so nothing is duplicated and login methods can grow.

## 7. Soft delete
`deleted_at` (nullable timestamp) or a `status` column instead of `DELETE`. Queries must exclude deleted rows. Combine with anonymization of personal fields.

## 8. Timestamps
Use `TIMESTAMPTZ` (timezone-aware) and store UTC. Keep `created_at` and `updated_at` on every table.

## 9. Naming conventions
- Tables, columns, databases: snake_case (`user_identities`, `display_name`, `gave_user`). Tables plural.
- PostgreSQL lowercases unquoted identifiers, so PascalCase names would need double quotes in every query. snake_case avoids that.
- Hibernate maps Java camelCase fields to snake_case columns automatically.
- Constraints and indexes get prefixes: `uq_` unique, `fk_` foreign key, `idx_` index.

## 10. Database vs. schema vs. table
- Hierarchy: server -> database -> schema -> table. SQL Server's default schema is `dbo`; PostgreSQL's is `public`.
- We use one database per service (`gave_user`) and the default `public` schema, so tables are referred to simply as `users`.
- Avoid reserved words as names. `user` is reserved in PostgreSQL, so the table is `users` (plural).

## 11. Database naming scheme
Databases are named `gave_<service>` (`gave_user`, later `gave_group`, `gave_expense`). The prefix identifies the application; the suffix identifies the owning service.

## 12. Flyway file naming
`V<version>__<description>.sql` (two underscores), in `src/main/resources/db/migration`. Applied in version order, recorded in `flyway_schema_history`. Never edit an applied migration; add a new version.

## 13. Design choices in V1 (users, user_identities)
- `gen_random_uuid()` default on UUID keys (built in since PostgreSQL 13) as a safety net; the app normally supplies IDs.
- `CHECK (email = lower(email))` stops duplicate accounts differing only by case.
- Status as `VARCHAR` + `CHECK` instead of a Postgres `ENUM`: adding a value later is a simple migration.
- Foreign keys are NOT indexed automatically in PostgreSQL (primary key and unique are). Add an index on FK columns to avoid full scans.
- Foreign key without `ON DELETE CASCADE`: the DB refuses to delete a parent that still has children, matching soft-delete design.
- `CHAR(3)` for ISO 4217 currency codes; `VARCHAR(320)` is the maximum valid email length.
- Deleted users keep a non-null placeholder email so `NOT NULL` and `UNIQUE` still hold.

## 14. Stored procedures, views, and JPA: our rule
- Default: JPA / Spring Data for writes and CRUD reads.
- Views: good for read-only read models and reports (e.g. balances); map as read-only entities or projections.
- Stored procedures/functions: exception only, for heavy set-based batch work once measured.
- Why not SPROC-first in the Java world: logic split across two places, harder to test and version, deploy coupling between app and DB, harder to scale than app instances, blurs the service boundary in microservices.
- Complex reads: derived queries, then JPQL/native `@Query`.
